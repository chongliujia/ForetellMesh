# 团队任务上下文对照 v1

本轮只诊断上一轮的任务状态混淆：当前任务已是两个电影合约，评估角色却原样复制了旧四合约评估。目标是检验历史上下文的呈现方式是否影响当前任务执行，不评估预测或交易效果。

## 固定案例和变量

来源为 `runs/qwen3_8b_team_data_catalogue_v1` 第二轮第一次 `research_task_assessor` 请求（调用索引 10），report SHA256 固定为 `28420e0afe4bf9c467f1b4b5486fc4d87a3a9b39eac3f71eb6cbd8b66730aa7e`。验证调用、尝试、目录和配置 artifact 哈希，并重建已准入训练目录。它是已暴露且已知失败的训练案例，不是独立测试。

两组保持完全相同的角色、提示、当前任务、历史规则、合约索引、当前数据目录、输出 schema、基础模型和生成参数。唯一改变的请求字段为 `upstream.training_history`：

- `full_history`：逐项复制归档请求，包含完整失败历史、旧提案正文和旧评估。
- `structured_history`：由程序提取过去失败状态、错误类型、失败实验指纹、原输出／请求／反馈哈希。删除旧回复正文和旧任务叙述；当前任务仍在相同的 `input.original_task` 中。完整历史留在注册输入及来源归档，不丢弃失败。

结构化组只读取调用索引 10 **之前**的调用及请求已携带的历史，不将本次已知错误、旧标准答案或其他实验臂输出加入输入。原失败输出仅在模型不可见的诊断字段中用于比较复现情况。

精简同时改变了历史内容和长度，因此不能将差异专门归因于某个 JSON 片段、单个旧 ID 或 token 数量。使用固定任务而非重跑整条研究链，避免上游任务变化混入比较。

## 预算与指标

`configs/team_context_comparison_v1.json` 注册固定顺序：完整、结构化、结构化、完整（ABBA）。同一冻结 Qwen3-8B-Base 只加载一次，贪心生成、上下文上限 12288、输出上限 1536；每次角色尝试最多一次格式修复，最多八次模型调用。各次调用独立请求，不把先前实验臂输出送给后续实验臂。

重复用于检查输出复现和顺序差异，**不是四个独立案例**。所有首次输出和修复均保留，分别统计首次有效和修复后有效，不只选最好的答案。

主要指标是评估列表是否严格覆盖当前两个合约、无旧合约混入，以及完整输出是否通过原验证器。模型仍可提出包含其他准入合约的新任务，所以只检查 `contract_assessments` 的多余 ID，不把任何位置提及旧 ID 都算作错误。次要记录延迟、输入 token 数、重复一致性和是否复现归档输出。

通过 schema 不证明提议的研究语义正确、数据充分、预测有效或团队自主改进。实验不调用协调决策、后续研究／数据／评分角色，不改生产研究协议、不触发训练、实盘或保留集评估。

## 能确认与不能确认的事

在这一已知训练案例中，历史呈现方式对任务执行产生了可复现的影响。精简过去失败记录、保留指纹和当前任务，消除了这次旧任务 ID 混入；这支持把“任务状态维护”与“模型本身的预测能力”分开诊断。

但结构化组仍用历史 Yes 成交价描述“票房与金融市场表现”的研究需求，尚未清楚区分实际票房和合约价格。路由正确不等于变量理解正确；没有形成或检验可执行预测方法。一次案例的贪心重复不能估计一般准确率，也不能说明只是旧回复正文（而非同时变化的长度、冗余和旧任务叙述）造成了全部错误。

下一步建议将同一结构化历史机制接回一个新的、限额完整研究协议，继续保留原始历史在审计文件，并检查协调决策、变量声明、数据绑定及计算是否也改善。要防止精简只让 JSON 更干净却遗漏有效失败信息；未经独立预测／交易效果验证，不触发微调或晋升策略。
